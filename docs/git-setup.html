The one-way remote
and why it is right for you

Cole's work flows into your repo. Nothing you write can flow back out to his. That property is enforced by three separate mechanisms in your git config — not by you remembering to be careful.

The problem, stated plainly

Three things have to be true at once, and they pull against each other.

  • Stay current. Cole is building fast — 74 commits between 31 August and 2 September 2026. You cloned his repo to watch that happen, so you need his newest work whenever you want it.
  • Never send anything to him. Your notes, your experiments, your eventual factory. None of it should reach his repository, deliberately or by accident.
  • Keep your own history. Your five onboarding docs live in the same tree as his code, and they have to survive every update he pushes.

A single ordinary clone gives you the first and fails the other two. What you have instead separates where work comes from from where your work goes.

First, what a "remote" actually is

One idea. Everything else on this page follows from it.

A remote is a nickname your laptop keeps for a copy of the project that lives somewhere else. It is nothing more than a name and an address written in a text file at .git/config.

Most people have exactly one remote, called origin, and they never think about it. git push sends to it and git pull takes from it, so "origin" and "the repo on GitHub" feel like the same thing.

They are not. You can have as many remotes as you like, and — this is the part that solves your problem — each remote can have a different address for reading than for writing. Git treats "where I fetch from" and "where I push to" as two separate settings that merely happen to match by default.

Your setup uses two remotes and, on one of them, deliberately breaks the write address.

Your setup, drawn

Two remotes. Cole's is named upstream and reads only. Yours is named origin and is the one plain git push talks to.

Why it is three locks, not one

Any one of these alone would stop your commits reaching Cole. You have all three, and they fail in different ways — which is the same reasoning the factory itself uses for its stop button.

Lock 1

The write address is deliberately broken

Cole's remote has a real read address and a fake write address. A push to it cannot half-work — it fails before touching the network.

Lock 2

You have no write access anyway

His repo belongs to coleam00. You are az9713. Even with a correct address, GitHub would refuse you.

Lock 3

Plain git push goes to your repo

Your branch is set to track origin/main, which is yours. You would have to type upstream on purpose to even attempt it.

Proof, rather than assurance — this is what actually happens if you try:

git push upstream main
fatal: 'DISABLED_never_push_to_cole' does not appear to be a git repository
fatal: Could not read from remote repository.

This is the same principle the factory is built on.

Cole's own rulebook says a gate written as an instruction is "a suggestion with good manners". His merge is a script, not a model deciding to merge. Your safety here is the same shape: a broken address in a config file, not a note telling you to be careful at 1am.

Staying in sync with Cole

Two commands do the whole job. Both are shortcuts stored in this repo's own config, so they exist here and in no other project on your machine.

Before anything: he has no releases

Worth knowing, because it removes a step you might go looking for. Cole publishes no tags and no releases — his repo has one branch, main, and nothing else. "His latest version" simply means his newest commits on that branch. There is no version list to choose from.

01

See what he has done

This downloads his work and lists it. It changes no file you have — it is a look, not a move. Run it as often as you like. 

git whatsnew

Nothing printed means you are already current. Otherwise you get one line per commit, oldest first, in the order he wrote them.

02

Read the detail, if you want it

His failure log is where the real learning is — every entry is a new rule and it names the code that now enforces it. This prints the new entries in full. 

git log -p main..upstream/main -- docs/incidents.md

Press q to get out of the pager when you are done reading.

03

Take it

This combines his work with yours and saves the result to your private repo. One command, and you are current and backed up. 

git sync
In sync with Cole, and pushed to your repo.

That is the whole routine. Nothing in it can reach Cole's repository, because git sync pushes to origin and only origin.

The one rule that keeps this effortless

Everything above stays easy as long as this holds.

Put your changes in files Cole does not have. Your five documents in docs/ are new filenames. He will never touch them, so combining his work with yours needs no decision from you — git can always do it silently.

If you edit a file he also edits — say template/factory/config.py — then one day you will both have changed the same lines. Git stops and asks you to choose. That is called a conflict, and it is the only genuinely awkward part of git for someone new to it.

If a merge ever stops and asks you something

Type this. It undoes the attempt completely and puts you back exactly where you were:

git merge --abort

Nothing is lost and nothing is broken. Then ask me and I will resolve it properly.

There is a second half to the same rule, and it matters more than it looks: do not run factory init in this folder. That command installs a working factory into a repository. Run it here and this clean reading copy becomes a running factory, every one of Cole's files gets local modifications, and every future update conflicts. Build your own factory in a different folder — this one stays the copy you read.

Why this is the right setup for you specifically

You are following someone else's build over weeks, taking notes as you go, and planning to build your own version later. That is a genuinely unusual shape: you are neither a contributor to his project nor an independent author of your own.

A contributor would want a fork, because sending work back is the point. An independent author would cut the cord entirely. You want to keep receiving indefinitely while never transmitting — and two remotes with one write address deliberately broken is the smallest arrangement that does exactly that.

It also degrades well. If you stop following Cole, delete one line from a config file and nothing else changes. If he adds a licence and you want to make your repo public, that is one command. Nothing here is a decision you have to live with.
